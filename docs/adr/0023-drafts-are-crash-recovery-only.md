# ADR 0023: 草稿只是崩溃兜底，退出清理不能被超时截断

## 状态

已接受（2026-11-01）

## 背景

[ADR-0001](0001-draft-recovery-with-mtime-conflict-resolution.md) 把草稿定义为「未保存修改的保命机制」；[ADR-0017](0017-close-interception-with-draft-flush-on-exit.md) 在 #346 修订出「关闭前先问一次」，#426 又明确了「不保存 = 真丢弃」。

这次讨论的起点是一个**误判**：初始判断认为「关闭单个标签」与其它两条路径语义不一致（以为选「不保存」仍会写草稿）。复核代码后确认**三条路径本来就一致**：

- `useTabClose` 的单标签与批量关闭都传 `keepDraft: choice !== "discard"`，即 `discard` → `false`；
- `doCloseTab` 收到 `keepDraft: false` 走 `session.dispose({ draft: "discard" })` → 删除草稿；
- `useTabClose.test.ts` 已有断言：`doCloseTab("tab1", { keepDraft: false })`。

所以「关闭时提示保存而不是记录草稿」在语义层面**已经是现状**。真正的问题在别处 —— 数据安全链上有一个真实缺口：

`useExitFlush` 把整段退出落盘包在 `Promise.race(…, 3000ms)` 里，而清理草稿是**逐个 `await`** 的。耗时随脏标签数线性增长，一旦撞满 3 秒，超时分支照样销毁窗口 —— 草稿没清完，下次启动内容就复活了。这正好对应用户描述的「我明明没保存，怎么又回来了」。

## 决策

### 1. 草稿的定位：仅崩溃兜底

草稿保留为技术机制（编辑期间周期性写入，用于进程被强杀 / 崩溃后的恢复），但**不承担正常关闭的保存职责**。正常关闭完成时该 tab 的草稿必须已被删除：

- 选「保存」：内容已落盘，`saveTo` 成功后 `deleteDraft`；
- 选「不保存」：用户明确丢弃，`dispose({ draft: "discard" })` 删草稿。

### 2. 退出前的草稿处理必须并行，且不能被 3 秒总超时截断到「没清完」

`flushAllDrafts` / `discardAllDrafts` 改为 `Promise.allSettled` 并行执行 —— 总耗时从「各标签之和」降到「最慢的一个」，在 3 秒预算内几乎必然完成。

**保留 3 秒兜底**：窗口必须关得掉，不能因为一次磁盘慢就永久卡住。因此这是「大幅降低概率」而非「数学上不可能」：极端情况下（磁盘长时间阻塞）仍可能残留草稿。要彻底消除，需要在启动时按「上次关闭的意图」清理，属于后续工作，不在本 ADR 范围内。

### 3. 三条关闭入口共用一套语义（事实记录）

| | 有未保存修改 | 保存 | 不保存 | 取消 |
|---|---|---|---|---|
| 关闭单个标签 | 汇总确认 | 真写盘（未命名另存为），失败即中止 | 真丢弃 + 删草稿 + 未命名内容清空 | 中止，标签保留 |
| 批量关闭标签 | 同上 | 同上 | 同上 | 中止整批 |
| 关窗 / 退出 | 同上 | 同上 | 同上 | 中止退出并复位状态机 |

实现上 `saveBeforeClose` 已是共用函数；本次不额外抽 `confirmUnsavedAndClose`（三处差异仅在「关闭动作本身」，强行合并会把三个调用点的上下文塞进一个函数，得不偿失）。

### 4. 关闭工作区 ≠ 关闭标签

`closeWorkspace()` 只清工作区状态，标签仍保留可编辑，因此不构成「关闭」语义、不触发关闭确认。

## 备选方案

**A. 彻底移除周期草稿** —— 崩溃即丢全部未保存内容。放弃：崩溃时用户没有机会做选择，这正是草稿唯一无法被「关闭时询问」替代的价值。

**B. 把退出落盘整体去掉超时** —— 保证清理一定完成，但违反 ADR-0017 的「窗口必须关得掉」（`destroy()` 兜底本来就是为了防止关不掉）。放弃。

**C. 启动时按「关闭意图」清理残留草稿**（写一个 purge 标记，下次启动先清） —— 能彻底消除残留，但引入新的持久化状态与跨启动协议。留作后续；本次先用并行把概率压到极低。

## 后果

**正面**

- 退出清理耗时不再随标签数线性增长，「超时导致草稿残留 → 内容复活」的概率大幅下降。
- 明确记录「三条关闭入口本来就语义一致」，避免后来者（包括我）再基于误判去改代码。
- 草稿职责单一化：只有崩溃恢复一条判据。

**负面**

- 仍是「尽力而为」：磁盘长时间阻塞时残留草稿依旧可能发生（已在决策 2 写明，不假装解决）。
- 用户误点「不保存」后没有任何找回手段 —— 这是 #426 已定的取舍，本 ADR 只是把它落实到三条路径。
- ADR-0001 的适用范围被收窄，阅读时需同时读本 ADR。
